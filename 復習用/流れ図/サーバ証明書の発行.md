# サーバ証明書の発行

## 前提と登場人物

**証明書を申請するのは運営者側の証明書管理クライアント、ドメイン管理を確認して署名するのはCA**である。これは発行の図であり、接続時の[証明書検証](証明書チェーン検証.md)とは別である。

以下は`example.com`のDNS管理権限を検証するACMEのDNS-01相当の構成例である。運営者は証明書管理クライアントと権威DNS、Webサーバを管理し、CAとの申請用アカウントは準備済みとする。ポーリング等の詳細は省略する。

## 1. CAがドメイン管理を確認する

```mermaid
sequenceDiagram
    autonumber
    participant C as 証明書管理クライアント
    participant A as 認証局CA
    participant D as example.comの権威DNS

    C->>A: 管理クライアントがexample.com用の証明書発行を申請する
    A-->>C: CAがDNS-01検証のchallenge情報を返す
    C->>C: 管理クライアントがchallengeと申請アカウントの鍵情報から応答値を作る
    C->>D: 管理クライアントが管理権限で_acme-challenge.example.comのTXTを設定する
    C->>A: 管理クライアントが検証準備の完了を通知する
    A->>D: CAが対象TXTレコードを問い合わせる
    D-->>A: 権威DNSが設定されたTXT値を返す
    A->>A: CAがTXT値を期待値と照合し、管理権限を確認する
    Note over A: CAが確認できなければ、この申請の証明書発行へ進まない
```

## 2. CAがCSRを確認して証明書を発行する

```mermaid
sequenceDiagram
    autonumber
    participant C as 証明書管理クライアント
    participant A as 認証局CA
    participant S as Webサーバ

    Note over C,A: 対象名の管理権限確認に成功した後
    C->>C: 管理クライアントがサーバ用鍵ペアを生成する
    C->>C: 管理クライアントが公開鍵とSAN等を含むCSRへ対応する秘密鍵で署名する
    C->>A: 管理クライアントがCSRを提出する<br/>サーバ用秘密鍵は含めない
    A->>A: CAがCSR署名・申請名との一致・発行条件を検証する
    alt CAの検証に成功した
        A->>A: CAが公開鍵・SAN・期限等を含む証明書へ発行用CA秘密鍵で署名する
        A-->>C: CAがサーバ証明書と必要な中間CA証明書を返す
        C->>S: 管理クライアントが保護された管理経路で鍵と証明書を設定する
    else CAの検証に失敗した
        A-->>C: CAが証明書の発行を拒否する
    end
```

サーバ用鍵をサーバ内やHSMで生成し、秘密鍵を移動しない構成もある。図の配備は運営者の管理範囲内で行い、CAへ秘密鍵を預けるという意味ではない。

</details>

## 処理後に残るもの

| 主体 | 保持するもの | 渡さないもの |
|---|---|---|
| 運営者側／Webサーバ | サーバ秘密鍵、サーバ証明書、中間CA証明書 | HTTPSの相手やCAへサーバ秘密鍵を送らない |
| CA | 発行記録、CA署名秘密鍵 | 申請者へCA秘密鍵を送らない |
| 権威DNS | 検証時の公開TXT値 | サーバ用秘密鍵は保持しない |

## 注意点

CSRの署名は「その公開鍵に対応する秘密鍵の保有」を示し、DNS検証は「そのドメインの管理権限」を確認する。CAの証明書署名は、それらを発行ポリシーの下で結び付ける。ACMEの申請アカウント鍵とサーバ証明書用の鍵も別の役割である。

DVは組織の実在性やサイト内容の安全性まで保証しない。発行に使うのは通常中間CAの鍵であり、ルートCAが毎回直接サーバ証明書へ署名するわけではない。HTTPによる検証等の別方式を、このDNS-01の図に混在させない。
