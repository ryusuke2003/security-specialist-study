# Webセキュリティ

## CSRFとCSRFトークン

- `CSRF`（Cross-Site Request Forgery）は、ログイン済み被害者のブラウザが持つ認証Cookieを利用し、攻撃者サイトから標的サイトへ意図しない状態変更リクエストを送らせる攻撃である。標的サーバには、正規利用者の認証Cookieが付いたリクエストのように見える。
- CSRFトークンは、リクエストが「正規サイトを表示した利用者の操作から作られた」ことを確認するための、十分に長いランダム値である。攻撃者は被害者の正規サイトのページを読み取れないため、被害者用の正しいトークンを取得できない。
- トークンが推測できると、攻撃者も偽リクエストに正しい値を入れられてしまう。したがって、推測・総当たりが現実的でないランダムな値にし、サーバ側で期待する値と照合する必要がある。単なる連番・時刻・利用者IDから作る値では不十分である。

```text
攻撃者サイト → 被害者ブラウザ → 標的サイト
                  認証Cookieは自動で付くことがある
                  CSRFトークンは正規サイトから読めないため付けられない
```

- CSRFトークンが必ず`localStorage`に保存されるわけではない。代表的な同期トークン方式では、サーバがセッションに期待値を保持し、正規サイトのHTMLの隠しフィールドや`meta`要素などへトークンを埋め込む。送信時にフォーム値やリクエストヘッダとして返し、サーバが照合する。
- 別の方式であるダブルサブミットCookieでは、トークンをCookieにも持たせ、同じ値をフォーム値またはカスタムヘッダでも送信させて一致を確認する。この場合も、認証CookieそのものをCSRFトークンにするのではない。
- `localStorage`にトークンを置き、JavaScriptがカスタムヘッダへ設定する実装もあり得る。しかし`localStorage`はJavaScriptから読めるため、XSSが起きると値を盗まれ得る。CSRF対策として必須の保存先ではなく、一般には同期トークン方式や適切なCookie属性を選ぶ。
- `SameSite`属性は、クロスサイトのリクエストに認証Cookieを付けにくくする補助的な対策である。状態変更にはCSRFトークン検証も併用し、`Origin`または`Referer`の検証も重ねる。

## SameSite属性

- `SameSite`は、サーバが`Set-Cookie`で指定するCookie属性である。ブラウザに対して「別サイトから始まったリクエストでは、このCookieを自動で付けるか」を指示し、認証Cookieを使うCSRFの起こりにくさを高める。
- ここでいう「サイト」は、概ね**スキーム（`https`など）と登録可能ドメイン**の組合せで決まる。たとえば`https://app.example.com`と`https://api.example.com`は同じサイトだが、`https://attacker.example`からのリクエストはクロスサイトである。

| 設定 | ブラウザがCookieを付ける主な範囲 | 使うときの注意 |
|---|---|---|
| `SameSite=Strict` | 同一サイトから始まったリクエストだけ | 別サイトのリンクから初めて開く場合にもCookieが付かず、利用者には未ログインのように見えることがある |
| `SameSite=Lax` | 同一サイトに加え、クロスサイトのトップレベル遷移のうち安全なメソッド（通常は`GET`） | 互換性とCSRF対策のバランスがよいが、状態変更を`GET`にしてはならない |
| `SameSite=None; Secure` | 同一サイト・クロスサイトの両方 | 外部サイトからの埋込みや連携で必要になることがある。`Secure`によりHTTPS通信に限定する |

- 例として、攻撃者サイトのフォームが標的サイトへ`POST`する場合、認証Cookieが`SameSite=Strict`または`Lax`なら通常はCookieが付かず、ログイン済みとして処理されにくい。`SameSite=None`ならCookie送信を許可するため、CSRFトークンなど別の防御が特に重要になる。
- SameSiteはCookieの自動送信を制限する仕組みであり、XSSや同一サイト内の脆弱性までは防げない。状態変更リクエストでは、SameSiteだけに頼らずCSRFトークンとサーバ側の`Origin`／`Referer`検証も組み合わせる。

## SQLインジェクションでいう「文字列連結」

- `+` 演算子の有無ではなく、**外部入力をSQL文のテキストへ直接組み込むこと**を指す。テンプレートリテラルや文字列補間でも同じく危険になり得る。
- 入力値を `'` で囲んでいても、SQLとして解釈される箇所に組み込む限り安全ではない。
- 対策は、SQL文と値を分離するプレースホルダ（プリペアドステートメント）を使うこと。
- プレースホルダは「ここから来るのは**値**」という値用の席（場所を確保する印）。先にSQLの構文を確定させ、後から渡す値をSQL構文として再解釈させない。単純な文字列置換ではない。

```js
// 危険：+ でなくても、入力値をSQL文に埋め込んでいる
`SELECT * FROM users WHERE name = '${input}'`

// 安全：? は値用の席。input はSQL文と別に値として渡す
db.query('SELECT * FROM users WHERE name = ?', [input])
```

- ただし、表名・列名・`ORDER BY` の順序などのSQL構文はプレースホルダにできない。利用者に選ばせる場合は、許可リストから固定の候補を選ぶ。

## 2026-08-17

### セッション管理とCookie属性

- セッション管理は、HTTPのようにステートレスな通信で、Cookieなどで渡された**セッションID**により各リクエストを同じ利用者・ログイン状態に対応付け、状態を管理する仕組みである。単に利用者情報を保存することではない。
- `Secure`はCookieをHTTPSでだけ送信して平文HTTPでの漏えいを抑える。`HttpOnly`はJavaScriptからCookieを読めなくして、XSS時のセッションID窃取を抑える。どちらもXSSの実行そのものを防ぐ属性ではない。

## 2026-08-21

### SSRF

- SSRF（Server-Side Request Forgery）は、Webアプリなどの**サーバ**に、攻撃者が指定した**内部向けURL**（`127.0.0.1`、プライベートIP、クラウドメタデータサービスなど）へリクエストを送らせる攻撃である。攻撃者が自分のブラウザから直接到達できない内部サービスにアクセスさせ得る。外部URLも指定できるが、特に危険なのは内部向けURLである。
- URLは許可リストで検証し、名前解決後の接続先IPも確認する。さらに、アプリサーバから内部・メタデータサービスへ不要な通信ができないようネットワーク分離と最小権限を組み合わせる。

## 2026-08-22

### XSSと表示時の対策

- XSSは、攻撃者が入力したデータをHTMLなどへ安全に変換せず出力した結果、閲覧者のブラウザでスクリプトが実行される脆弱性である。主対策は、保存時の置換ではなく、**表示直前に出力先の文脈に応じて行う出力エンコーディング**である。
- `HttpOnly`はJavaScriptによるCookie読取りを抑えるが、XSSのスクリプト実行そのものは止めない。XSS対策の代替ではなく、被害を抑える補助策として扱う。

## 2026-08-23

### 入力検証と出力エンコーディングの役割分担

- **入力検証**は、データを受け取るときに、業務上許可する文字種・長さ・形式をallowlistで確認し、想定外の値を処理へ入れない対策である。サーバ側で必ず実施する。
- **出力エンコーディング**は、データをHTML本文・HTML属性値・JavaScript・URLなどへ表示する直前に、その出力先の文脈に合わせて特殊文字を安全な文字列へ変換し、データを構文として解釈・実行させない対策である。
- 入力検証を通らない保存済みデータや外部連携の値もあり得るため、XSS対策としては両方を行い、特に出力時のエンコーディングを省略しない。SQLインジェクション対策のプレースホルダによるパラメータ化は、SQL構文と値を分離する別の対策である。

### WAF

- WAF（Web Application Firewall）は、利用者とWebアプリの間でHTTP/HTTPSリクエストを検査する防御機構である。SQLインジェクション、XSS、ディレクトリトラバーサルのような既知の攻撃パターンを検知し、遮断・記録・警告できる。
- WAFログでは、いつ、どの送信元が、どのURLやパラメータに対し、どの検知ルールで、遮断または許可されたかを確認できる。インシデント調査では、アプリログの「読めたか」と組み合わせ、攻撃の試行・遮断・漏えい範囲を追う。
- WAFは誤検知や未知の攻撃を完全には防げないため、入力検証、出力エンコーディング、認可、パラメータ化などアプリ側の対策を置き換えない。
