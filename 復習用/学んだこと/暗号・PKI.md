# 暗号・PKI

## 暗号化と署名は違う

- 暗号化の目的は「中身を読めなくすること」。

- 署名の目的は「誰が作ったか・改ざんされていないかを確認すること」

## サーバ証明書に入っている主な内容

**証明書（Certificate）の中には、CAが署名する対象である `tbsCertificate` と、その対象に対するCAのデジタル署名である `signatureValue` の両方が入っている。**

```text
Certificate
├─ tbsCertificate  ← CAが署名する対象部分
│  ├─ シリアル番号
│  ├─ 署名アルゴリズム
│  ├─ Issuer（発行したCA）
│  ├─ 有効期限（Not Before / Not After）
│  ├─ Subject（証明書の対象者）
│  ├─ サーバの公開鍵
│  ├─ 公開鍵アルゴリズム
│  └─ 拡張情報
│     ├─ SAN（利用を許可するドメイン名）
│     └─ Extended Key Usage（例: serverAuth）
│
├─ signatureAlgorithm  ← CAが署名に用いたアルゴリズム
└─ signatureValue      ← tbsCertificateに対するCAのデジタル署名
```

- `tbsCertificate` は「署名対象部分」であり、CAの署名値そのものではない。ブラウザはここをハッシュ化し、`signatureValue` を発行者CAの公開鍵で検証して対応を確認する。
- `signatureAlgorithm` は、`tbsCertificate` 内にも署名アルゴリズム情報として含まれる。外側の `signatureAlgorithm` と整合していることも確認対象である。
- Webサーバの接続先名は、現在では主にSANで確認する。Subjectだけで接続先名を判断しない。
- ブラウザは署名に加え、有効期間、SANの接続先名一致、証明書チェーン、必要に応じて失効状態を確認してから証明書を信頼する。

## TLSで「相手を信頼して通信を続ける」流れ

```text
1. 証明書でWebサーバの身元を確認する
2. ECDHE鍵交換で、双方が同じ共有秘密をそれぞれ計算する
3. 共有秘密から通信ごとの鍵を導出し、以後のデータを暗号化・認証する
```

- 「共通鍵を持っていること」だけが身元証明なのではない。最初に証明書と `CertificateVerify` でWebサーバの身元と秘密鍵の保持を確認する。
- TLS 1.3では、Webサーバの公開鍵で共通鍵を暗号化して送るわけではない。公開鍵暗号技術の一種であるECDHE鍵共有を使い、ブラウザとWebサーバが一時公開鍵を交換して、双方が自分の一時秘密鍵と相手の一時公開鍵から同じ共有秘密を計算する。共通鍵そのものはネットワーク上を送らない。
- ブラウザは証明書検証に成功してから、その共有秘密から導出した鍵を「認証済みのWebサーバとの通信鍵」として受け入れる。
- 以後はAES-GCMやChaCha20-Poly1305などのAEADで、暗号化と改ざん検知用の認証タグをセットで使う。受信側は、正しい通信鍵を知る相手だけが作れる認証タグを検証する。
- 感覚的には、最初に証明書で「あなたは誰か」を確認し、その後は「二人だけが導出した通信鍵で正しい認証タグを作れているか」を確認し続ける。これにより、同じ認証済み相手との通信が継続していることと、途中改ざんがないことを確かめる。

### mTLSで確認できるもの

- mTLS（相互TLS）では、サーバ証明書に加えてクライアントも証明書を提示し、対応する**クライアント秘密鍵を保持していること**をTLSハンドシェイクで証明する。
- したがってmTLSが主に確認するのは、**そのクライアント証明書と秘密鍵を使える端末・ソフトウェア（ワークロードを含む）**である。証明書を端末、サービス、組織などへどのように発行・管理したかに応じて、その識別子をアクセス制御に利用できる。
- ただしmTLSだけで「実際に操作している人」が誰かを直接証明するわけではない。証明書・秘密鍵の共有や漏えいがあれば他者も使えるため、個人の本人確認が必要ならログイン、MFAなどを別途組み合わせる。

## HTTPとHTTPSの違い

| 性質 | HTTP | HTTPS（HTTP over TLS） |
|---|---|---|
| 機密性 | 通信内容を暗号化しないため、途中で読まれ得る | TLSで通信内容を暗号化する |
| 完全性 | 改ざんされても検知できない | AEADの認証タグなどで改ざんを検知する |
| サーバ認証 | 接続先が本物のサーバか確認できない | 証明書で、接続先ドメイン用の秘密鍵を持つサーバか確認する |

- HTTPでは盗聴だけでなく、攻撃者が途中で応答を書き換えたり、偽サーバへ誘導したりできる。
- 通常のHTTPSが主に認証するのはサーバ側である。利用者側の本人確認は、ログインや必要に応じたクライアント証明書で別に行う。

## TLSはHTTP専用ではない

TLSはHTTPだけの技術ではなく、上位プロトコルの通信を暗号化・改ざん検知・相手認証で保護するための汎用的な層である。典型的には、アプリケーションプロトコルの下、TCPの上で使われる。

| 上位プロトコル + TLS | 代表的な用途・呼び名 |
|---|---|
| HTTP + TLS | HTTPS |
| SMTP + TLS | メール送信経路の保護 |
| IMAP / POP3 + TLS | メール受信の保護 |
| LDAP + TLS | LDAPSなど、ディレクトリサービス通信の保護 |
| FTP + TLS | FTPS |

- SMTP、IMAP、POP3、LDAPなどでは、最初からTLSで接続する方式のほか、平文接続後に `STARTTLS` でTLSへ切り替える方式もある。
- TLSが保護するのは通信路であり、各アプリケーションの認証・認可の設計そのものを置き換えるものではない。

## 2026-08-21

### ハッシュとMAC

- ハッシュ関数は任意長のデータから一定長のハッシュ値を計算する。受信側も同じデータからハッシュ値を計算して照合すれば、データの変更を検知できるが、ハッシュ値だけでは誰が作ったかは確認できない。
- MACはメッセージと**共有秘密鍵**から計算する認証子である。鍵を知る相手だけが正しいMACを作れるため、完全性に加えて送信者の真正性を確認できる。ハッシュは鍵なし、MACは鍵ありと区別する。

### CSRと証明書発行

- CSR（Certificate Signing Request）は、申請者が公開鍵、組織情報、SANなどを含めてCAへ送る証明書発行要求である。CSRは対応する秘密鍵で署名するが、**秘密鍵そのものをCAへ送らない**。
- CAはドメインなどの所有確認を行った上で、申請された公開鍵と識別情報を含む証明書へCAの秘密鍵で署名して発行する。

## 2026-08-22

### ホスト名検証ではSANを使う

- `CN`（Common Name）はSubject内の名前属性で、従来はサーバ証明書に対応するホスト名を1つ記載する用途で使われた。一方、複数のドメイン名を一つの証明書で扱うには、拡張領域の`SAN`（Subject Alternative Name）へ`dNSName`を複数並べる。
- ただし、SANが使われる理由は「CNには1個しか書けないから」だけではない。現在のTLSクライアントは、接続先名の照合先としてSANを標準的に使う。1ドメインだけの証明書でもSANへ記載する。
- 例えば`www.example.jp`と`api.example.jp`を同じ証明書で使うなら、SANに両方の名前を入れる。接続先が`api.example.jp`なら、クライアントはSAN内にその名前（又は有効なワイルドカード）があることを確認する。
- CNは古い実装との互換のためSANがない場合に参照されることがあるが、SANが存在する証明書ではSANの照合結果を優先する。Subjectの組織名やCNがもっともらしくても、SANが接続先名と一致しなければホスト名検証は失敗する。
- SANにはDNS名のほかIPアドレス、メールアドレス、URIなども表せる。`https://192.0.2.10/`へIPアドレスで接続して検証する場合は、DNS名ではなくSANのIPアドレス項目との一致が必要である。

## 2026-08-23

### AEADとnonce

- AEADは、暗号化による機密性と認証タグによる改ざん検知を同時に提供する方式である。AES-GCMなどでは、同一鍵でnonceを再利用すると安全性が崩れるため、送信ごとに一意なnonceを使う。
- 受信側は認証タグを検証し、失敗したデータを復号結果として利用せず破棄する。
- 流れ: [AEADの暗号化と認証タグ検証](../流れ図/AEADの暗号化と認証タグ検証.md)

## 2026-08-24

### AEADは安全な組合せを方式として定める

- AEADは、**暗号化と認証を一体化して、正しい対象・順序・検証ルールを方式側で定めた仕組み**と捉える。
- 暗号化とMACを別々に組み合わせるだけでは、認証対象や順序を誤る危険がある。AEADは暗号文とAADを認証対象にし、認証タグが有効な場合だけ平文を利用する、という規則まで含める。

## 2026-08-26

### Webhookでハッシュだけでは足りずHMACを使う理由

- 鍵なしハッシュは、受信側が本文から再計算して一致を確認できる。しかし攻撃者が本文と添付ハッシュ値の両方を置き換えられる通信では、攻撃者も新しい本文のハッシュを計算できるため、改ざん検知にも送信者確認にも使えない。
- HMACは本文と共有秘密鍵から計算する。共有秘密を知らない攻撃者は、改ざんした本文に対応する正しいHMACを作れないため、WebhookではHMACを検証する。失敗したリクエストは処理せず、拒否・記録する。

## 2026-08-27

### Webhookは公開URLへ届くリクエストの送信元確認が必要

- Webhookでは、自分のシステムが相手サービスへ取りに行くのではなく、相手サービスがイベント発生時に**自分の公開URLへHTTPリクエストを送る**。受信側はインターネットから到達可能な入口を持つことになる。
- HTTPSなら通信経路の盗聴・改ざんを防げるが、そのURLへ届いたリクエストが「連携を許可した正規サービスからの通知」であることまでは保証しない。公開URLには攻撃者もリクエストを送れるため、受信側で正規性を検証してから処理する必要がある。
- 典型的には、相手サービスが本文（必要に応じて時刻などの署名対象）と共有秘密からHMACを作り、署名ヘッダとして送る。受信側は受信した生の本文から同じHMACを再計算して照合し、一致した場合だけイベントを処理する。不一致なら拒否して記録する。
- 送信元IPの許可リストは、相手が固定の公式IP範囲を公開している場合の補助策にはなる。しかしIP変更・経路・運用上の事情があるため、IPアドレスだけに依存せず、署名検証を中心にする。再送やリプレイも考え、署名対象の時刻・イベントID・重複処理対策も確認する。

### MACとHMACの違い

- `MAC`（Message Authentication Code）は、メッセージと共有秘密鍵から認証子を作り、改ざんされていないことと、共有秘密を知る相手が作ったことを確認する**仕組み全体の呼び名**である。
- `HMAC`（Hash-based MAC）は、ハッシュ関数を使ってMACを作る**具体的な方式の一つ**である。例えばHMAC-SHA-256はSHA-256と共有秘密鍵を使う。
- したがって、HMACはMACの一種であり、「MACとHMAC」は並列の別概念ではない。MACにはHMACのほか、ブロック暗号を使うCMAC、GCMの認証部分を使うGMACなどもある。
- HMACは単純な`hash(鍵 + 本文)`ではなく、鍵を定められた方法で内側・外側へ組み込む構成である。実装では独自に連結して作らず、ライブラリのHMAC実装を使い、受信側との比較はタイミング差が出にくい比較関数で行う。

## 2026-09-05

### MACは電子署名ではない

- MACは送信側と受信側が同じ秘密鍵を共有し、メッセージから認証子を生成・検証する。完全性と共有鍵を知る相手からの送信であることは確認できるが、双方が同じMACを作れるため第三者に対する否認防止にはならない。
- 電子署名は署名者だけが持つ秘密鍵で署名し、検証者は公開鍵で検証する。MACを「共通鍵で署名する」と覚えず、**共有秘密鍵ならMAC、秘密鍵と公開鍵の組なら電子署名**と区別する。

### SANがない証明書は現代のホスト名検証で失敗する

- 以前はSubjectの`CN`にドメイン名を書き、ホスト名検証に用いる方式が使われていた。SANは複数の名前を列挙できるだけでなく、**「この証明書がどの名前に対して有効か」**を明示するための専用フィールドであるため、現在はこちらが正規の照合先になった。
- 証明書チェーンの検証では、CA署名・信頼の連鎖・有効期限・失効状態などを確認し、**信頼できるCAが発行した有効な証明書か**を確かめる。しかし、それだけでは「いま接続しようとしている`api.example.jp`用の証明書か」までは分からない。例えば、正規CA発行の`www.example.jp`用証明書を提示されても、`api.example.jp`への接続で受け入れてはならない。
- そこでホスト名検証として、接続先名をSANの`dNSName`（IPアドレス接続なら`iPAddress`）と照合する。**チェーン検証は証明書の信頼性、SAN照合は接続先ドメインへの適合性**を確認する役割分担であり、両方が成功して初めてその接続先のサーバとして受け入れる。
- 現在の標準（RFC 9525）では、サービスの接続先名は`subjectAltName`で表し、Subjectの`CN`を使って照合してはならない。したがって、SANを持たずCNだけにホスト名を入れた証明書は、現代的なTLSクライアントではホスト名検証に失敗すると考える。
- これは証明書の署名や有効期間とは別の検証である。チェーン検証に成功していても、接続先名がSANの`dNSName`と一致しなければ接続を拒否する。
- 旧実装や組織内の互換設定でCNを代替参照する場合はあるが、例外であり、設計・運用・試験問題ではCNフォールバックを前提にしない。IPアドレスで接続する場合は、DNS名ではなくSANの`iPAddress`が完全一致しなければならない。

### FQDNとIPリテラルではSANの型を分ける

- `FQDN`は**Fully Qualified Domain Name**の略で、DNS階層上の位置を省略せず、ルートまでたどれる完全なドメイン名である。ホストを表す例として`www.example.com`があり、厳密な表記ではルートを表す末尾のドットを付けて`www.example.com.`と書く。通常のURLや会話では末尾のドットを省略してもFQDNと呼ぶことが多い。

```text
www.example.com.
│   │       │ └─ ルート（末尾のドット）
│   │       └── TLDのラベル: com
│   └────────── 第2レベルのラベル: example
└────────────── ホストを識別する左端のラベル: www
```

- 検索ドメイン`example.com`が自動補完される前提で入力する`www`のような短縮名は、その文脈がなければ完全な位置を決められない。FQDNは`www.example.com`のように、接続先をDNS名前空間上で一意に特定できるところまでラベルを並べる。
- FQDNは`www`から始まる名前という意味ではない。`api.example.com`も、ゾーン頂点を表す`example.com`も、ルートまでの完全な名前として扱われるならFQDNである。
- TLSクライアントはURL全体を証明書と文字列比較するのではない。例えば`https://www.example.com:8443/login`から接続先のhostである`www.example.com`を取り出す。`https`というスキーム、`8443`というポート番号、`/login`というパスは、SANのDNS名照合には含めない。
- クライアントは接続先hostがDNS名なら`DNS-ID`、IPv4またはIPv6のIPリテラルなら`IP-ID`という別種の参照識別子として扱う。証明書側でも、SAN（`subjectAltName`）のGeneralNameはDNS名用の`dNSName`とIPアドレス用の`iPAddress`に分かれている。

| 接続先URL | クライアントが照合する値 | 証明書のSANで必要な型 |
|---|---|---|
| `https://www.example.com/` | DNS名`www.example.com` | `dNSName`（表示例: `DNS:www.example.com`） |
| `https://192.0.2.1/` | IPv4アドレス`192.0.2.1` | `iPAddress`（表示例: `IP Address:192.0.2.1`） |
| `https://[2001:db8::1]/` | IPv6アドレス`2001:db8::1` | `iPAddress`（表示例: `IP Address:2001:db8::1`） |

- したがって、証明書に`dNSName`として`192.0.2.1`相当の文字列が入っていても、`https://192.0.2.1/`への接続で必要な`IP-ID`との一致にはならない。見た目が同じ文字列でも、**参照識別子とSAN項目の型が違えば不一致**である。
- `iPAddress`は証明書内部では文字列ではなく、IPv4なら4オクテット、IPv6なら16オクテットのアドレス値として格納される。照合はパース後のアドレス値をオクテット単位で行うため、IPアドレスにワイルドカードやサブネット単位の部分一致は使わない。
- DNS名の比較はASCIIでは大文字・小文字を区別しない。ワイルドカードを許す場合も、原則として`*.example.com`のように左端ラベル全体へ置き、`www.example.com`には一致するが、`example.com`や`a.b.example.com`には一致しない。
- 現在のサーバID検証では、DNS名はSANの`dNSName`、IPアドレスはSANの`iPAddress`と照合し、Subjectの`CN`は照合に使わない。覚え方は、**FQDNならDNS型、IPリテラルならIP型。文字列が似ていても型をまたいで照合しない**。
- 参照: [RFC 8499（DNS Terminology）](https://www.rfc-editor.org/rfc/rfc8499.html)、[RFC 9525（Service Identity in TLS）](https://www.rfc-editor.org/rfc/rfc9525.html)、[RFC 5280（PKIX Certificate and CRL Profile）](https://www.rfc-editor.org/rfc/rfc5280.html)

## 2026-09-03

### AEADの認証タグは「人」ではなく「鍵を知る者」が作ったデータを確認する

- AEADの認証タグを検証して確認できるのは、暗号文・AAD・nonceが改ざんされておらず、**共通鍵を知る者**がそのタグを作れた、というデータの完全性・真正性である。
- これはログイン認証のように「いま操作しているのはどの利用者・アカウントか」を識別して確認する本人認証とは別の役割である。利用者を特定するには、パスワード、MFA、WebAuthn、クライアント証明書などの認証機構と、認証後のアカウント情報を別途扱う。
- 共通鍵を複数の主体が共有していれば、全員が正しいタグを作れる。そのためタグだけからは、共有者のうち**誰が**送信したかを区別できず、鍵が漏えいした場合も攻撃者が正しいタグを作れてしまう。否認防止を含む個人・組織単位の送信者特定には、通常は電子署名など別の仕組みを使う。
- 覚え方: **認証タグ＝データと鍵の認証、ログイン＝人（アカウント）の認証**。流れは[AEADの暗号化と認証タグ検証](../流れ図/AEADの暗号化と認証タグ検証.md)を参照する。
