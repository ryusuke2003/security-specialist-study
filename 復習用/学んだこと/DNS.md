# DNS

## DNSSECのRRSIG検証

- `RRSIG`は自分で検証するものではない。キャッシュDNSサーバの検証処理が、受信DNSデータ・`RRSIG`・`DNSKEY`（公開鍵）を使い、署名が有効かを判定する。
- 署名側は、正規化したDNSレコード群などの署名対象をハッシュ化して指紋`A`を作り、秘密鍵で署名して`RRSIG`を作る。検証側は受信データから指紋`A'`を作る。
- RSA方式では、「公開鍵で`RRSIG`を処理して署名時の指紋`A`に対応する値を確認し、`A'`と照合する」と考えてよい。ただし、元のDNSデータを復元する処理ではない。
- ECDSAやEd25519では、`RRSIG`を指紋`A`へ戻さない。公開鍵・`RRSIG`・指紋`A'`を使う数式で、直接`OK / NG`を判定する。
- 方式が異なっても目的は同じで、**「この受信DNSデータに対応する署名か」**を検証すること。`RRSIG`と`DNSKEY`にあるAlgorithm番号から、使う検証方式を判断する。
- 2026-08時点で代表的に推奨される方式は、`8: RSASHA256`、`13: ECDSAP256SHA256`、`15: ED25519`。ルートゾーンのKSKは同時点で`8: RSASHA256`を使用している。

## 2026-08-23

### DNSSECとは

- DNSSECは、DNS応答に電子署名を付け、**正当なゾーンの秘密鍵によって署名され、途中で改ざんされていないこと**を検証する仕組みである。DNSキャッシュポイズニングなどで偽の名前解決結果を受け入れることを防ぐ。
- `RRSIG`はDNSレコード群への署名、`DNSKEY`は`RRSIG`を検証する公開鍵、`DS`は親ゾーンが公開する子ゾーンの**特定の`DNSKEY`**から計算したダイジェストを含むレコードである。`DS`と対応する`DNSKEY`の照合により、親ゾーンから子ゾーンのDNSKEYへ信頼をつなぐ。
- DSに対応する鍵（典型的にはKSK）はDNSKEY RRsetの`RRSIG`を検証する起点となる。A RRsetなどの`RRSIG`は、検証済みDNSKEY RRsetに含まれる適切な鍵（典型的にはZSK）で検証する。DSに対応する鍵がA RRsetへ直接署名するとは限らない。
- 検証するキャッシュDNSサーバは、`DS`と`DNSKEY`の対応、および`DNSKEY`による`RRSIG`の検証が成功したときだけ、DNS応答を利用・キャッシュする。署名済みで信頼の連鎖にあるゾーンで検証に失敗した応答は、通常`SERVFAIL`として扱い、未署名応答へ黙ってフォールバックしない。
- DNSSECはDNS通信の**暗号化**や利用者の**秘匿**を行うものではない。通信経路の秘匿にはDoTやDoHなど、別の仕組みを用いる。

## 2026-08-24

### DNSSECの信頼の連鎖を目的からたどる

1. 最終的に確認したいのは、**A RRsetの真正性・完全性**である。
2. A RRsetの`RRSIG(A)`を検証するには、子ゾーンの検証済み`DNSKEY RRset`に含まれる適切なDNSKEY（典型的にはZSK）が必要である。
3. 子ゾーンのDNSKEYを信頼するには、親ゾーンから得た`DS`と、DSに対応する子ゾーンDNSKEYをハッシュ化して照合する。
4. そのDNSKEYを起点に、`RRSIG(DNSKEY)`を検証してDNSKEY RRset全体を信頼する。
5. ただしDS自体も信頼できなければならないため、親ゾーンのDNSKEYで`RRSIG(DS)`を検証する。
6. 親ゾーンのDNSKEYも同じように、さらに上位の親ゾーンのDSとRRSIGをたどって信頼する。
7. この連鎖を最後までたどると、あらかじめ保持する**ルートTrust Anchor**に到達する。

つまり、`DS`は親から子のDNSKEYへ信頼をつなぐ照合材料、`DNSKEY + RRSIG`はDNSデータの署名を検証する組合せである。

## 2026-08-27

### DNSSECの信頼の連鎖（`.jp` → `example.jp` の例）

- 目標は、たとえば `www.example.jp` の **A RRset が正規のゾーンで署名され、改ざんされていないこと（真正性・完全性）**を確認することである。その `RRSIG(A)` を検証するには、`example.jp` の検証済み `DNSKEY RRset` が必要になる。
- あらかじめ信頼している起点は、検証リゾルバに設定されたルートゾーンの **Trust Anchor（ルートDNSKEY）**だけである。以下を上から順に検証して、信頼を子ゾーンへ渡す。

  1. ルートDNSKEYで、親であるルートが署名した `.jp` の `DS RRset` の `RRSIG(DS)` を検証する。
  2. 取得した `.jp` の `DNSKEY` のうち、上のDSのダイジェストと一致する鍵を確認する。その鍵で `RRSIG(DNSKEY)` を検証し、`.jp` の `DNSKEY RRset` 全体を信頼する。
  3. 検証済みの `.jp` DNSKEYで、`.jp` が署名した `example.jp` の `DS RRset` を検証する。
  4. `example.jp` のDNSKEYとDSを照合し、その鍵で `RRSIG(DNSKEY)` を検証して、`example.jp` の `DNSKEY RRset` を信頼する。
  5. 検証済みの `example.jp` DNSKEYで、目的の `A RRset` に付く `RRSIG(A)` を検証する。

- 覚え方は、**DSは親から子のDNSKEYを信頼するための照合値、RRSIGは各RRsetが改ざんされていないことを確かめる署名**。`DS → 子DNSKEYの照合 → RRSIG(DNSKEY)の検証` をゾーンごとに繰り返し、最後に `RRSIG(A)` を検証する。

### 再帰DNSサーバーとキャッシュDNSサーバーは役割の呼び分け

- **再帰DNSサーバー**は、利用者端末の代わりにルートDNS、TLD DNS、権威DNSをたどり、名前解決を完了させる役割である。
- **キャッシュDNSサーバー**は、取得したDNS応答をTTLの範囲で保存し、次回の同じ問合せへ素早く返す役割である。
- 実運用では、一台のDNSサーバーが両方の役割を担うことが多い。そのため「再帰DNSサーバー」と「キャッシュDNSサーバー」は別製品を指すというより、同じサーバーのどの働きを強調するかによる呼び分けとして理解するとよい。

```text
利用者端末
  ↓ 問合せ
再帰・キャッシュDNSサーバー
  ├─ キャッシュあり → 保存済みの応答を返す
  └─ キャッシュなし → 権威DNSまでたどって取得し、TTLの範囲で保存して返す
```

- 例えばGoogle Public DNSなどへ問合せたときも、このようにキャッシュを先に確認し、なければ再帰的な名前解決を行う。
