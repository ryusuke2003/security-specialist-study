# DNS

## DNSSECのRRSIG検証

- `RRSIG`はDNSレコード群（RRset）への電子署名で、検証DNSリゾルバが受信したRRset・`RRSIG`・検証済み`DNSKEY`を使って有効性を確認する。
- 重要なのは署名アルゴリズムごとの計算方法ではなく、**「正当なゾーンの鍵で署名され、途中で改ざんされていないRRsetか」を確認する**こと。署名方式ごとの内部計算やAlgorithm番号は暗記対象にしない。

## 2026-08-23

### DNSSECとは

- DNSSECは、DNS応答に電子署名を付け、**正当なゾーンの秘密鍵によって署名され、途中で改ざんされていないこと**を検証する仕組みである。DNSキャッシュポイズニングなどで偽の名前解決結果を受け入れることを防ぐ。
- `RRSIG`はRRsetへの署名、`DNSKEY`はその署名を検証する公開鍵、`DS`は親ゾーンから子ゾーンのDNSKEYへ信頼をつなぐための照合情報である。
- 検証リゾルバは、親側で検証済みの情報を起点に`DS → 子DNSKEY → 子ゾーンのRRSIG`と信頼をつなぎ、最後に目的のA RRsetなどを検証する。
- 信頼の連鎖にある署名済み応答の検証に失敗した場合は、通常`SERVFAIL`として扱い、未署名応答へ黙ってフォールバックしない。
- DNSSECはDNS通信の**暗号化**や利用者の**秘匿**を行うものではない。通信経路の秘匿にはDoTやDoHなど別の仕組みを用いる。
- 流れ: [DNSSEC](../流れ図/DNSSEC.md)

## 2026-08-24

### DNSSECの信頼の連鎖

1. 検証リゾルバは、あらかじめ信頼するルートのTrust Anchorを起点にする。
2. 親ゾーンの検証済みDNSKEYで、子ゾーンの`DS`が正しいことを確認する。
3. `DS`と子ゾーンの`DNSKEY`を照合して、そのDNSKEYを信頼する。
4. 検証済みの子DNSKEYで、目的のA RRsetなどに付いた`RRSIG`を検証する。

覚え方は、**DSは親から子の鍵へ信頼を渡す、DNSKEYは署名検証用の公開鍵、RRSIGはRRsetへの署名**である。

## 2026-08-27

### 再帰DNSサーバーとキャッシュDNSサーバーは役割の呼び分け

- **再帰DNSサーバー**は、利用者端末の代わりにルートDNS、TLD DNS、権威DNSをたどり、名前解決を完了させる役割である。
- **キャッシュDNSサーバー**は、取得したDNS応答をTTLの範囲で保存し、次回の同じ問合せへ素早く返す役割である。
- 実運用では、一台のDNSサーバーが両方の役割を担うことが多い。そのため「再帰DNSサーバー」と「キャッシュDNSサーバー」は別製品を指すというより、同じサーバーのどの働きを強調するかによる呼び分けとして理解するとよい。

```text
利用者端末
  ↓ 問合せ
再帰・キャッシュDNSサーバー
  ├─ キャッシュあり → 保存済みの応答を返す
  └─ キャッシュなし → 権威DNSまでたどって取得し、TTLの範囲で保存して返す
```

## 2026-09-13

### DNSSECのsecure / insecure / bogus

- セキスペ対策では、DNSSEC検証結果をまず`secure`・`insecure`・`bogus`の3状態で区別できればよい。

| 状態 | 意味 |
|---|---|
| `secure` | 信頼の連鎖と署名検証に成功した |
| `insecure` | DNSSECを使っていないことが正当に確認できた |
| `bogus` | DNSSECで保護されるはずなのに検証に失敗した |

- 重要なのは、`insecure`と`bogus`は違うこと。DNSSECを使っていないだけの`insecure`は通常の名前解決結果として利用できる場合があるが、**署名付きであるべきデータの検証に失敗した`bogus`は信用してはいけない**。
- 親のDSから子のDNSKEYまで信頼できても、そのDNSKEYで目的のRRsetの`RRSIG`検証に失敗したら`bogus`である。
- `bogus`になる原因には、データ改ざんだけでなく、RRSIGの期限切れや署名更新漏れなどもある。
- 覚え方: **secure＝検証OK、insecure＝DNSSECなし、bogus＝DNSSEC検証NG**。
