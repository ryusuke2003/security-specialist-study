# 認証・認可 / IAM

## 2026-08-21

### SAMLによる認証連携

- SAMLは、IdP（Identity Provider）が認証した利用者の情報を含むSAML Assertionを、SP（Service Provider）へ渡してシングルサインオンを実現するXMLベースの認証連携標準である。
- SPはAssertionをそのまま信用せず、IdPの署名、発行者、宛先、対象者、有効期限などを検証する。IdPが利用者を認証し、SPが検証済みAssertionに基づいて利用を許可する役割分担を押さえる。

## 2026-08-23

### OAuth 2.0 / OIDCとPKCE

- OAuth 2.0はAPIへのアクセス権限を委譲する**認可**の枠組みであり、OIDCはその上にIDトークンを加えて利用者を確認する**認証**の仕様である。
- 認可コードフローではブラウザへアクセストークンを直接返さず、クライアントがトークンエンドポイントで認可コードを交換する。これは強い資格情報であるアクセストークンをブラウザやURLに露出させにくくし、交換時にPKCEの`code_challenge`と`code_verifier`を照合して、その認可要求を始めたクライアントだけが交換できるようにするためである。公開クライアントは秘密を安全に保持できないため、認可コードを横取りされてもPKCEで交換を防ぐ。

### 認可コードフローのフロントチャネルとトークン交換

- Authorization Endpointは、利用者のログイン・MFA・同意という人間の操作を扱うため、**ブラウザを使うフロントチャネル**として設計されている。WebアプリがブラウザをIdPへ誘導し、認証・同意後にIdPは`302 Found`とリダイレクトURIを返す。ブラウザがそのURIへ移動して、Webアプリのcallbackへ認可コードを渡す。
- IdPがWebアプリのバックエンドへ認可結果を直接通知する設計も技術的には可能だが、通常のAuthorization Code Flowは「ユーザーが使っているブラウザを元のアプリへ戻す」方式である。ブラウザが戻ることと`state`の照合により、どのブラウザセッションが開始した認可フローかを自然に対応付けられる。
- ブラウザ経由のリダイレクトには短命・一回限りの**認可コード**だけを載せ、アクセストークンはリダイレクトと分離したToken Endpointで取得する。PKCEを使うフローでは、認可コードを単独で入手しても`code_verifier`がなければ交換できない。サーバーサイドWebアプリでは通常バックエンドとIdPの通信になる一方、SPA・モバイルアプリでは端末上のクライアントがToken Endpointへ直接接続する。いずれも、ブラウザのURLへアクセストークンを返さない点が重要である。

## 2026-08-24

### PKCEのcode_verifierを保持する場所

- **公開クライアント**とは、OAuth/OIDCにおいてクライアントシークレットを安全に隠しておけないアプリのことである。利用者端末で動くSPAやモバイルアプリは、配布したプログラムや端末内の値を利用者・攻撃者が解析できるため、通常は公開クライアントとして扱う。
- `client_secret`は次回以降も同じ値を使う長期秘密であるため、SPAやモバイルアプリではコード・設定・バイナリ・端末ストレージなどへ永続保存せざるを得ず、アプリを解析されると取り出され得る。公開クライアントに長期の`client_secret`を置いても、秘密として扱えない。
- `code_verifier`はログイン開始時にランダム生成し、認可コードをトークンへ交換する数分間だけメモリなどに保持して破棄する一時値である。事前にアプリを解析しても、そのログインで使う値はまだ存在しないため、横取りした認可コードだけでは交換できない。`client_secret`が家に常置する合鍵なら、`code_verifier`は入場時だけ作る使い捨ての合言葉と考えるとよい。
- ただしPKCEは端末やブラウザが完全に侵害されても安全にする仕組みではない。生成後の`code_verifier`を端末上のマルウェアやXSSで読み取られれば盗まれ得る。PKCEが主に防ぐのは、認可コード単体の横取りによるトークン交換である。
- サーバーサイドWebアプリでは、`code_verifier`はバックエンドのサーバー側で生成・保持する。ブラウザは認可コードをリダイレクトで受け、Webアプリのサーバーへ渡すが、トークン交換で`code_verifier`を認可サーバへ送るのはサーバー側である。
- SPAやモバイルアプリでは、利用者端末上のアプリが`code_verifier`を生成・保持し、認可コードを受けてトークン交換時に送る。アプリが端末上で動く公開クライアントであっても、認可コードだけを横取りした第三者は`code_verifier`を知らないため交換できない。
- 推奨される`S256`方式では、`code_verifier`をSHA-256でハッシュし、Base64URLエンコードして`code_challenge`を作る。認可要求には`code_challenge`だけを送り、Token Endpointで受け取った`code_verifier`から認可サーバが同じ値を再計算して照合する。十分にランダムな`code_verifier`なら、見えている`code_challenge`から元の値を現実的に逆算することは困難である。
- PKCEが確認する「同じクライアント」は**ユーザー本人**ではなく、認可処理を開始したときに`code_verifier`を生成・保持したクライアントである。ユーザーの認証・同意はIdPが行い、PKCEは認可コードをトークンへ交換する主体を結び付ける。
- SPAでは最終的にアクセストークンがブラウザ上に存在するため、XSSなどでアクセストークン自体を盗まれるリスクはPKCEだけでは防げない。XSS対策、トークンの短命化、保存方法の設計などが別途必要になる。
- BFF（Backend for Frontend）やサーバーサイドWebアプリでは、アクセストークン・リフレッシュトークンをバックエンドだけに保持し、ブラウザには`HttpOnly`なセッションCookieなどだけを持たせられる。この場合、トークンはバックエンドと認可サーバ間で取得・保持され、ブラウザへ直接露出させにくい。
- 要点は、認可コードをトークンへ交換するクライアントが最初から`code_verifier`を持ち続け、認可要求では変換値の`code_challenge`だけを出すことである。流れは[OAuth 2.0 / OIDCの認可コードとPKCE](../流れ図/OAuth2とOIDCの認可コードとPKCE.md)を参照。

## 2026-08-27

### 認証と認可を分ける理由

- **認証（authentication）**は「あなたは誰か」を確定する処理である。ログイン成功後に`user_id = 123`のような利用者識別子を得るところまでが認証である。
- **認可（authorization）**は「その利用者に、この操作を許可してよいか」を判定する処理である。例えば`user_id = 123`がadminロールを持つか、削除APIの実行を許可されているかを確認する。

```text
ログイン成功 → 利用者を識別する（認証）
             ↓
各API・画面の操作時 → ロール・権限・条件を確認する（認可）
```

- 認証できたことを「何でもしてよい」と扱うと最小権限を守れず、一般利用者・管理者・経理担当などの操作範囲を適切に分けられない。
- 認証ロジックに「このメールアドレスなら管理者」「この利用者なら削除可能」のような権限判断を混ぜると、権限変更のたびにログイン処理まで変更することになり、変更漏れや権限チェック漏れが起きやすい。
- 分離しておけば、認証は利用者の識別に集中し、認可はロール・属性・対象リソース・操作ごとの規則として変更できる。監査ログでも「誰が操作したか」と「どの規則により許可・拒否したか」を分けて追跡できる。
- OAuth 2.0は主に認可、OIDCは認証を補う仕様である。この役割の違いを保つと、IDトークンで利用者を確認することと、アクセストークン／スコープでAPIアクセスを許可することを混同しにくい。
- **要点**: 認証と認可を分離すると、それぞれの責務が明確になって処理が複雑化しにくく、権限やログイン方式の変更にも強くなる。
