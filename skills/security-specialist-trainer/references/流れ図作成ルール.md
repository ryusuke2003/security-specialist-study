# 流れ図作成ルール

セキュリティプロトコルや認証・認可など、複数主体のやり取りを図解するときの共通ルールである。ユーザーが流れ図を求めた場合、および採点後の復習資料として `復習用/流れ図/` を作成・更新する場合に適用する。

## 作成前

1. `復習用/流れ図/` を全件確認し、同じ学習目的の図があれば更新して再利用する。
2. 複数の主体、処理順、分岐、信頼、データ移動のいずれかを追う必要がある場合だけ図を作る。単純な定義は文章で説明する。
3. 通信の順序を示すときは `sequenceDiagram`、保持状態・分岐・依存関係を補足するときは `flowchart` を使う。

## 図に必ず含める情報

- 主体は「利用者」「RPサーバー」「ブラウザ／OS」「認証器」のような具体的な役割名にする。「システム」「処理側」だけで済ませない。
- 各通信矢印には、**誰が、誰へ、何を送るか**が分かる送信物を書く。「要求」「応答」「認証」のような抽象語だけにしない。利用者の操作を示す矢印には、選択・入力・承認などの具体的な操作を書く。
- 受信後に検証・照合・保存するものが重要なら、受信者を主語にした自己処理として明記する。
- 登録、認証、認証後の通常通信など、目的と保持状態が変わる段階は分ける。
- 鍵、資格情報、チャレンジ、コード、Cookie、トークンなどについて、永続保持・一時保持・毎回送信の違いを明記する。
- フローの最後に「認証後／処理後に誰が何を保持するか」を表または図でまとめる。
- 秘密鍵、生体情報、パスワードなど、**送られないもの・相手が保持しないもの**が誤解されやすい場合は明記する。
- 成功時と失敗時で状態が変わる重要な箇所だけ分岐を描く。

## 説明の粒度

各段階が次の問いへ答える粒度にする。

1. 誰が処理を開始するか。
2. 送信者は、何を、誰へ送るか。
3. 受信者は、受け取った何を、どの保持情報と照合・検証するか。
4. 成功または失敗によって、どの主体の状態がどう変わるか。
5. 処理後に各主体が保持するものと、保持しないものは何か。

仕様上の内部データをすべて列挙する必要はない。試験学習上の因果関係を理解するために必要な送信物・検証対象・保持物を具体化する。

## 完了確認

- 主体名だけを読んで役割を区別できる。
- 各矢印だけを読んで送信者・受信者・送信物を説明できる。
- 検証者と、検証に使う情報を説明できる。
- 秘密情報がどこに残り、どこへは送られないかを説明できる。
- 認証後または処理後の通常通信で使う資格情報を説明できる。
- Mermaidコードブロックの開始・終了、participant名、矢印、分岐の対応が正しい。
