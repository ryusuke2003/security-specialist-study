# 流れ図作成ルール

直接の作図依頼と、採点後に`復習用/流れ図/`を作成・更新するときに適用する。作図・文書保守だけなら学習用の共通開始処理は行わない。

## 作成前

1. ファイル一覧と[流れ図ガイド](../../../docs/流れ図ガイド.md)で既存図を探し、同じ目的なら更新する。通常は関連図だけを読み、全件確認は全体監査の依頼時に限る。
2. 複数の主体、順序、分岐、信頼やデータ移動を追う場合だけ図にする。単純な定義は文章にする。
3. `## 前提と登場人物`に、何を説明する図か、端末内／端末外、事前共有済みの鍵・設定、方式・構成、意図的に省略した変種を書く。サーバーサイドWebアプリとSPAなどを同じ図に混ぜない。

## 主語と矢印

- 通信や人の操作には`sequenceDiagram`を使い、`autonumber`を置く。登場する全IDを`participant`または`actor`で明示し、表示名を具体的な役割にする。
- 矢印の文言にも「ブラウザが…を送る」「RPが…を返す」のように主語と動作を書く。通信なら送信物、人なら入力・承認などの操作を示す。「要求」「処理」「認証」だけにしない。
- 検証・計算・保存・権限判断は担当主体への自己矢印で示す。受信した何を、どの保持情報・鍵で検証するかを明記する。内部処理を架空の通信として描かない。
- Cookie・状態表・DMARC等のデータやルールを通信相手にしない。同じ端末内のブラウザ・認証器などを分けた場合は、その境界を前提で説明する。
- 分岐や計算依存には`flowchart`を使う。ノード内にも「FWが…を判断する」のように主語を置き、矢印が通信・処理順・計算依存のどれかを説明する。実装が行わない照合や比較を創作しない。

## 分割と情報量

登録、認証、認証後の通常通信、準備、実データ転送など、目的と保持状態が変わる段階を分ける。別方式の比較も分ける。短い見出しを付け、分割した続きが成功時だけなら図の冒頭で示す。

一つの矢印には一つの中心的な操作を置く。目安は一図20操作以内とし、長い図は段階で分ける。ただし検証対象や失敗時の停止を省いて短くしない。長い文言は`<br/>`で改行し、暗号の計算式や任意項目は図の外へ置く。

## 状態・成功・失敗

- 状態が変わる重要な検証には成功・失敗の扱いを書く。図が成功経路だけを示すなら、前提と停止条件を明記する。
- 認証と認可、署名と暗号化、送信前拒否と送信後の読取り拒否、操作指示と実行成功を区別する。
- `## 処理後に残るもの`で主体ごとの鍵・資格情報・Cookie・トークン・ログ等を表にする。永続保持・一時保持・毎回送信の違い、秘密鍵等を送らない境界を必要に応じて書く。
- `## 注意点`で保証しないことや実装依存の条件を補い、`## 参照資料`に仕様・公式文書などの一次資料を付ける。仕様更新は根拠を確認し、単なる簡略図を全方式共通の動作と説明しない。

## 検証と完了

1. 構造検査を実行する。

   ```bash
   python3 -m unittest discover -s skills/security-specialist-trainer/tests -p 'test_流れ図.py' -v
   ```

2. 変更した**全Mermaidブロックを実際にレンダリング**し、構文エラー、文字切れ、重なり、過度な横幅、主体と矢印の対応を目視する。使ったMermaidの版を記録する。構造テストは技術内容の正しさや表示成功の証明ではない。レンダリングできない場合は未確認と報告する。
3. 一次資料と見比べ、送信物、検証者と検証鍵、失敗時の状態、処理後の保持者を説明できることを確認する。
4. 既存ファイル名と参照リンクを保つ。図の追加・構成変更ではガイドも更新する。生成SVG・PNG、作業用HTML、キャッシュをリポジトリへ残さず、学習記録・理解度を作図だけで変更しない。
