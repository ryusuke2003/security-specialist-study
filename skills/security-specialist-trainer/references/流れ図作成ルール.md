# 流れ図作成ルール

直接の作図依頼と、採点後に`復習用/流れ図/`を作成・更新するときに適用する。作図・文書保守だけなら学習用の共通開始処理は行わない。

## 作成前

1. [流れ図ガイド](../../../docs/流れ図ガイド.md)で既存資料を探し、同じ目的なら更新する。通常は関連資料だけを読み、全件確認は全体見直しの依頼時に限る。
2. `## 前提と登場人物`で、図の目的、端末内／外、方式・構成、鍵・設定の準備、意図的に省略した変種を明記する。単純な定義だけなら図を増やさない。
3. セキスペ合格に必要な理解へ寄与するか確認する。正答や近接概念の区別に不要な規格の細部、実装固有の例外、派生方式を図へ詰め込まない。原理や主体・順序の理解を助ける補足は許可するが、主図の読解負荷を上げる場合は詳細側へ分離し、暗記必須事項として扱わない。

## まず読める概要図を置く

各資料の主図は`## 全体像`のSVGとする。横長の詳細シーケンス図をそのまま画像にするのではなく、主体と情報の受渡しを上から追える概要へ整理する。目安は4〜8操作、最大12操作とし、別方式や条件別の経路は段階名で区別する。原則として前提・失敗条件を残し、詳細を省いて一般化しない。

原稿は同じMarkdownの「図の内容を文字で読む」折り畳み内へ置く。`<!-- overview:start -->`〜`<!-- overview:end -->`に`要点:`、`補足:`と、`段階 / 種類 / 主体 / 相手 / 内容`の5列表を一つ書く。セル内に縦棒は使わない。

種類は`送信`・`交換`・`内部`・`確認`・`並行`から選ぶ。送信・交換では両主体を明記する。内部・確認は相手を`—`とし、検証・計算・保存を架空の通信にしない。並行は担当する二主体を書く。本文には具体的な操作・対象・検証鍵等を置き、「認証」「処理」だけにしない。図の主体欄で主語を明示する。

```bash
python3 skills/security-specialist-trainer/scripts/render_overviews.py
python3 skills/security-specialist-trainer/scripts/render_overviews.py --check
```

生成した`復習用/流れ図/画像/<資料名>.svg`を相対画像リンクと内容を表すalt文で埋め込み、原稿と一緒にコミットする。SVGを直接編集せず、原稿を修正して再生成する。別のJSON原稿や外部画像サービスを追加しない。

## 詳細図と保持情報

- 詳細な手順・分岐は「詳しい手順・分岐を開く（Mermaid）」に残す。登録／認証／通常通信など、目的が違う段階を分ける。概要と詳細で主体・鍵・送信物・停止条件を矛盾させない。
- シーケンス図は`autonumber`を使い、全主体を`participant`または`actor`で宣言する。矢印にも主語と動作を書く。内部処理は自己矢印にする。Cookie・状態表等を通信相手にしない。
- フローチャートのノードにも主語を書く。通信、処理順、計算依存のどれを示すか説明する。一図は目安20操作以内にし、必要なら段階で分ける。
- 認証と認可、署名と暗号化、送信前拒否と受信後の読取り拒否、指示と実行成功を区別する。成功経路だけならその前提と失敗時の停止を示す。
- `## 処理後に残るもの`に主体ごとの鍵・資格情報・Cookie・ログ等を表で残す。永続・一時・送らないものを区別する。
- `## 注意点`で保証しないこと・実装依存を補い、`## 参照資料`へ仕様・公式文書等の一次資料を付ける。

## 検証と完了

全件テストとSVGの`--check`を実行し、変更した全SVGをブラウザ等で表示する。文字切れ・重なり・主体・矢印・段階の読順を確認する。詳細Mermaidを変更したらその全ブロックも描画する。構造テストを、表示や技術内容の正しさの証明にしない。

一次資料と照合し、検証者・検証鍵・失敗時・保持者を説明できるか確認する。未確認部分はPRに明記する。図の追加・構成変更ではガイドも更新し、既存ファイル名とリンクを保つ。

教材SVGは残すが、確認用PNG・HTML、キャッシュ、旧版コピーは追加しない。学習記録・理解度を作図だけで変更しない。監査・測定の報告書は作らず、変更理由と確認結果をPR本文へまとめる。
